# ScoreSync — Holistic Gap & Quality Review

ScoreSync is a multi-role event scoring platform for LGU municipal festivals, covering event creation, judge scoring, results tabulation, and payment tracking. The core flows are mostly wired up, but a cluster of incomplete features, role/data mismatches, and security problems make it not production-ready. The most dangerous issues are hardcoded Firebase credentials in source control, an unauthenticated privilege-escalation endpoint in the production route file, and a broken organizer experience where the toolbar is invisible due to a role variable mismatch.

**Watch for:** hardcoded Firebase API key and session secret in committed source; `/fix-role` endpoint with no auth in production routing; participant dashboard has no record of events already joined; organizer event-detail toolbar is dead code due to `isEncoder` vs `isOrganizer` mismatch; `deleteEvent` leaves orphaned subcollections that corrupt analytics.

---

## High-level view

The participant role is the most incomplete. The join form writes to `event_participants`, but nothing ever reads that collection back. After joining, a participant has no confirmation, no history view, and no cancel option. The sidebar offers only "Browse Events" — no "My Registrations" link exists anywhere in the codebase.

Several controllers pass `isEncoder: role === "encoder"` to views, but the stored role is `"organizer"`. The `injectUser` middleware handles the mapping correctly, but controller-level locals override middleware locals, so organizers see a blank toolbar on the event detail page and broken sidebar sections on the events list. This is a systemic misalignment across `eventController.js`, `inventoryController.js`, and `analyticsController.js`.

Every role-specific sidebar link for judges ("Score Entry"), organizers ("Contestant Entry"), and participants ("Browse Events") points to `/events`. These were clearly development stubs that were never replaced. A judge clicking "Score Entry" lands on the full events list with no guidance.

The `/fix-role` endpoint is registered with zero authentication middleware and accepts `?role=superadmin` for any email address. Combined with the hardcoded `SESSION_SECRET` fallback and the real Firebase credentials committed in `firebaseConfig.js` and `.env.example`, the security posture is critical.

The organizer dashboard's "Ongoing Now" stat renders garbage due to a Handlebars anti-pattern (`{{@index}}` inside `{{#each}}` instead of a server-computed count). The `users/index.xian` stats bar omits participant and superadmin counts despite the controller computing and passing both values. Neither is catastrophic, but both indicate incomplete wiring between controller and view.

`deleteEvent` issues a single `deleteDoc` on the event document. Firestore subcollections (`contestants`, `criteria`, `scores`) are not cascade-deleted and accumulate silently. Score submission accepts values outside the criterion's `maxScore` bound. Tabulation preferences are read by scanning the `users` collection for the first admin doc found, which is non-deterministic with multiple admins.

<details>
<summary>Issues (13)</summary>

1. **Hardcoded Firebase credentials in source** — `firebaseConfig.js` embeds the real `apiKey`, `appId`, `authDomain`, `messagingSenderId`, and `measurementId` as literal fallbacks. The `.env.example` contains the same values. Remove the literals and require env vars only.

2. **`/fix-role` unauthenticated in production routing** — `router.get("/fix-role", fixRole)` has no auth middleware. Any visitor can promote any account to `superadmin` via `?email=x@x.com&role=superadmin`. Remove the route or gate it behind `requireRole("superadmin")` plus a one-time token.

3. **Hardcoded `SESSION_SECRET` fallback** — `index.js` falls back to `"scoresync-secret-2026"`. With the secret public, session cookies can be forged. Remove the fallback string and enforce the env var.

4. **Participant "My Registrations" is entirely missing** — `event_participants` is written on join but never read back to the participant. No route, no view, no sidebar link. Add `GET /participant/registrations`, a corresponding view, and a sidebar entry under `{{#if isParticipant}}`.

5. **`isEncoder` vs `isOrganizer` mismatch breaks organizer toolbar** — `eventController.js`, `inventoryController.js`, and `analyticsController.js` pass `isEncoder: role === "encoder"`. The stored role is `"organizer"`. The `{{#if isEncoder}}` toolbar block in `show.xian` is dead for all real organizers. Fix to `isEncoder: role === "organizer"` to match the middleware, or stop passing it from controllers and let middleware locals be authoritative.

6. **`isOrganizer` never passed by `eventController.js`** — `listEvents` and `showEvent` don't pass `isOrganizer`. Because controller locals shadow middleware locals in hbs rendering, `{{#if isOrganizer}}` blocks in `show.xian` and `events/index.xian` are always false for organizers, even though `injectUser` set it correctly.

7. **Organizer "Ongoing Now" stat always wrong** — `{{#each activeEvents}}{{#if (eq status 'ongoing')}}{{@index}}{{/if}}{{/each}}` outputs concatenated loop indices, not a count. Compute `ongoingCount` in `dashboardController.js` and pass it to the template.

8. **`deleteEvent` leaves orphaned subcollections** — Deleting the event document does not delete `contestants`, `criteria`, or `scores` subcollections. These accumulate silently and cause analytics to process stale data from deleted events. Add explicit subcollection cleanup before the parent delete.

9. **`deleteUser` does not revoke Firebase Auth** — `deleteDoc` removes the Firestore profile but not the Firebase Auth account. The deleted user can still log in; `loginUser` reads the empty profile as `{}` and assigns the default `"participant"` role. Requires Firebase Admin SDK to fully revoke access.

10. **Score submission has no bounds validation** — `submitScores` accepts any numeric value. There is no check against the criterion's `maxScore`. A judge can submit 9999 on a 100-point criterion, silently corrupting the weighted average.

11. **`tabPrefs` loaded non-deterministically** — `loadTabPrefs()` scans `users` and takes the first admin's `tabPrefs`. With multiple admins, Firestore does not guarantee order, so tabulation precision and the Olympic rule may vary between scoring sessions. Store system settings in a dedicated Firestore document.

12. **`users/index.xian` stats bar omits Participant and Superadmin counts** — `participantCount` and `superAdminCount` are computed and passed by `listUsers` but not rendered. The "Total" tile count will exceed the sum of visible role tiles.

13. **`/debug-session` left in production routing** — `router.get("/debug-session", requireAuth, ...)` exposes `userId`, `userName`, and `userRole` to any authenticated user. Remove it.

<summary>Details</summary>

## Participant join works; participant history doesn't exist

`joinEvent` validates the event, prevents duplicate joins, and writes to `event_participants` with full contact info and a `"registered"` status. That collection is never read again anywhere in the codebase. The participant dashboard queries only `activeEvents` for the join form. There is no `myRegistrations` export in `participantController.js`, no `GET /participant/registrations` route, and no sidebar link under `{{#if isParticipant}}`. A participant returning to the app after joining has no affordance to find what they signed up for.

## `isEncoder` / `isOrganizer` mismatch breaks organizer toolbar

Three controllers pass `isEncoder: req.session.userRole === "encoder"`. The stored role is `"organizer"`. The `injectUser` middleware maps this correctly — `res.locals.isEncoder = role === "organizer"` — but controller-level view locals override `res.locals`, so every organizer session gets `isEncoder: false` on pages rendered by those controllers.

In `show.xian`:
```handlebars
{{#if isEncoder}}
  <a href="...contestants/add">Add Contestant</a>
  <a href=".../results">Results</a>
{{/if}}
```
This block is dead code for all real organizers. The same controller never passes `isOrganizer`, so the sidebar's `{{#if isOrganizer}}` section also fails on those pages. The fix is either to stop passing these flags from controllers entirely and rely on middleware locals, or to consistently derive them from `role === "organizer"` in every controller that renders a view with role-gated blocks.

## Security: hardcoded credentials and unauthenticated privilege escalation

`firebaseConfig.js` has the production project's full credential set as literal fallbacks. The `.env.example` contains the same real values. Anyone with repo access has read/write access to the live Firestore database and can create Firebase Auth accounts directly.

`routes/index.js`:
```javascript
router.get("/fix-role", fixRole);
```
No middleware. The handler accepts `?email=x@x.com&role=superadmin` and writes any role to any Firestore user document. There is no token, no IP restriction, no rate limit. A comment in the source says "one-time use, then remove" — it was not removed.

`index.js`:
```javascript
secret: process.env.SESSION_SECRET || "scoresync-secret-2026",
```
With the secret known, session cookies can be forged for any `userId`.

The `/debug-session` route exposes session internals to any logged-in user, not just admins.

## Orphaned subcollections on event deletion

`deleteEvent` issues `deleteDoc(doc(db, EVENTS, req.params.id))`. Firestore does not cascade subcollection deletes. After the call, `events/{id}/contestants`, `events/{id}/criteria`, and `events/{id}/scores` persist in the database. `runAIAnalytics` iterates all events and fetches their subcollections — it will pick up score data from deleted events if they are queried by ID. The `payment_records` top-level collection stores `eventId` references that become dangling after deletion, surfacing "Unknown Event" entries in the inventory view that can never be cleaned up through the UI.

## Score submission accepts out-of-range values

```javascript
const score = parseFloat(rawScore);
if (isNaN(score)) continue;
```

The criteria document's `maxScore` is loaded in `scoringPage` to build the input matrix but is not re-fetched in `submitScores`. A submitted value of 150 on a `maxScore: 100` criterion passes through unchanged, and `resultsPage` will compute a weighted score above the criterion's defined ceiling. Client-side `max` attributes on inputs are not a sufficient guard.

## `tabPrefs` loaded non-deterministically

`loadTabPrefs()` does a full `users` collection scan, finds the first doc where `role === "admin"`, and returns its `tabPrefs`. The scan has no `orderBy`, so Firestore returns documents in insertion order, which is not stable across reads. With multiple admins who have divergent settings — one with `olympicRule: true`, another with `olympicRule: false` — the tabulation rule applied to a given scoring session is arbitrary. The `olympicRule` changes whether the highest and lowest judge scores are dropped, which directly affects final rankings. Storing `tabPrefs` in a top-level `settings` document eliminates the ambiguity.

## Sidebar navigation links are placeholder stubs

The sidebar for all non-admin roles uses `/events` as the href for every action link:

- Judge: "Score Entry" → `/events`, "View Results" → `/events`
- Organizer: "Contestant Entry" → `/events`, "View Results" → `/events`
- Participant: "Browse Events" → `/dashboard`
- Admin: "Criteria Setup" → `/events`, "View Results" → `/events`

A judge clicking "Score Entry" lands on the full events list with no filter or guidance. For the judge role specifically, the "Score Entry" link should target `/events` filtered to `status=ongoing` or — better — a dedicated `/scoring` landing page that shows only events with active scoring sessions. The participant "Browse Events" link is identical to "Dashboard", making the sidebar section pointless.

## `deleteUser` does not revoke Firebase Auth

`deleteDoc` removes the Firestore profile. The user's Firebase Auth credential is untouched. On their next login, `signInWithEmailAndPassword` succeeds, `getDoc` returns an empty snapshot, `profile` is `{}`, and `loginUser` assigns the default role `"participant"` with status implicitly treated as approved. The "deleted" user re-enters the system as an anonymous participant. Full deletion requires calling `admin.auth().deleteUser(uid)` via the Firebase Admin SDK, which is not currently imported anywhere in the project.
